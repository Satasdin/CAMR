Incidents and how they were handled (no code under camr/, tests/ or configs/ was changed)
-----------------------------------------------------------------------------------
1. Ollama server stopped mid-sweep (~30 min in) because the background process
   it ran under hit a session time limit. From then on every request failed with a
   connection error, but the harness still marked those runs 'completed'
   (0 ok queries). Affected run_ids 6-24: qwen2.5:7b treatment/gsm8k (1/12 ok) and
   every llama3.1:8b, gemma2:9b and qwen2.5:14b run (0 ok).
   Fix: these 19 runs were set to status='failed' in camr.sqlite (rows kept, not
   deleted), Ollama was restarted, and the sweep was resumed so they re-ran.

2. Out-of-memory kills during gemma2:9b. The llama-server process behind Ollama
   was killed 3 times by the container's memory limit at ~13.4 GB anon RSS.
   Its prompt cache (llama.cpp default cap 8192 MiB) grew on top of the model
   weights. Two runs lost queries: run 35 gemma2:9b treatment/hotpotqa (28/30 ok)
   and run 37 gemma2:9b treatment/gsm8k (11/12 ok). (A third kill hit between
   queries and cost no query.) Both runs were set to status='failed' and re-run
   clean as runs 39 and 40.
   Fix: Ollama was restarted with LLAMA_ARG_CACHE_RAM=1024, which caps the
   llama-server prompt cache at 1024 MiB. The server log confirmed it:
   "prompt cache is enabled, size limit: 1024 MiB".
   This affects prefill reuse only, not model outputs or decode speed. Runs under
   each setting:
     default 8192 MiB cache: all qwen2.5:7b runs (1-5, 25), all llama3.1:8b runs
                             (26-31), gemma2:9b runs 32-34 and 36
     1024 MiB cache:         gemma2:9b runs 39-40, all qwen2.5:14b runs (41-46)
   No OOM kills or failed queries after the change.

   Run 38 (qwen2.5:14b floor/popqa) has status 'interrupted' with 0 queries. It was
   stopped on purpose during the server restart and was redone as run 41.
